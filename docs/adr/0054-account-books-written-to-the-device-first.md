# 0054. An account's books are written to the device first and sent after

- Status: Accepted
- Date: 2026-11-28

## Context

An account reads and writes its space in Supabase directly, with no copy on the device ([ADR 0046](0046-the-books-in-use-follow-who-is-signed-in.md)). With no network its pages say the books cannot be reached, and a write that fails is not kept. The site is now used by a small group of acquaintances who keep real games in their accounts ([ADR 0052](0052-sign-in-with-google-and-a-first-entry-agreement.md)), and a game is often played where the network is poor or comes and goes. A buy-in that cannot be recorded at the table is a buy-in lost.

M6 step 2 is sync. Its first part, D.2, is to write the books to the device first and send them when there is a network. The organizer agreed the design on 2026-11-28. This is its data layer; how the app shows what is still to send is the next pull request. Merging by time of change (D.1) and devices kept in step as they change (D.3) are not part of it.

The database is as it is: no migration, no new grant or policy. The guest's books on the device are not touched.

## Options considered

- Keep only the ledger on the device and the rest online: a game, its players and its settings would still need the network, and a game could not be opened offline.
- One database on the device for every account, records told apart by space: a sign-out would have to delete them record by record, and a bug in one query could show one space's records in another's.
- **A copy of each space on the device, in a database of its own**, that pages read and write as a guest's books are read and written, with the changes still to send kept beside it.
- Sending each record as it now stands: simple, but a record changed twice offline and a delete in between are lost in the order.
- **An outbox of changes in the order they were made**, each kept in the same local transaction as the write it comes from.
- Merging the copy with what the account holds by the time each record changed: needs times and deletion marks on the records, which is D.1.
- **A pull that makes the copy what the account holds**, but for records with a change still to send.

## Decision

- **One database a space.** An account's space has its own IndexedDB database on the device, `holdem-account-<space ID>`, with the tables of a set of books and their indexes, as the guest's have them from version 8, plus `outbox` and `meta`. The guest's database (`holdem-guest`, eight versions) is the same as before; a test holds its name, version and tables. Pages still import `repository` from `data/index.ts`, which for an account is now `createAccountRepository` in `data/account-repository.ts`: it reads the copy through the guest's Dexie repository and writes it with the change to send.
- **Every write keeps its change in the same transaction.** A save, the own record made if missing, events added to the ledger, and a delete of an insurance hand, a saved setting or a summary each add one entry to the outbox, ordered by an increasing number, with the records it touches as `list:id`. Both are written or neither is. A record is checked where it is written, as it was before it was sent ([ADR 0044](0044-books-in-postgres-as-documents.md)): another organizer's fails with `ForeignOrganizerError` and one the backup's schemas do not allow with `StorageError`, and neither reaches the outbox. The ledger stays append-only on the device too: an event's ID already there fails, and an undo is a reversal event. A delete of a record the copy does not hold, with nothing waiting for it, sends nothing, as the account does not hold it either as far as the device knows.
- **The sender** (`data/sync.ts`) sends the outbox oldest first, one change at a time, and deletes each entry once the account has it. The order keeps a game ahead of its events, insurance hands and summary, which the database holds to by its foreign keys. It runs after every write, when the browser reports the network back (`online`), when the app comes back to the front (`visibilitychange`), when the books open, and after a wait that doubles from 2 seconds to at most a minute while tries fail. It sends only while its books are the ones in use: when the books change hands, the last account's sender is stopped before the next account's books are opened. It sends nothing while the client is signed in as anyone but the account the books are for (the session it keeps in this browser), and an answer that comes back after the session changed is taken as waiting, never as a refusal. One tab sends at a time: the sender and the pull share a Web Lock, `holdem-account-sync.<space ID>`, held across tabs, and a page with no Web Locks falls back to a lock within itself.
- **Sending again is safe**, so a change whose answer was lost is sent again as if new:
  - Ledger events are added with `insert … on conflict (organizer_id, id) do nothing` (supabase-js `upsert(…, { ignoreDuplicates: true })`). It needs no right to change a row, and `ledger_events` has only `select` and `insert` for `authenticated` (`20261120000000_accounts_and_books.sql`); `on conflict … do update` is refused there, as the database itself answered. An event is never changed, so one with the same ID is the same event. A batch is all or none on the server too.
  - The host's own record is sent as `ensure`, with `ignoreDuplicates` as before, never as a save: when two devices each make it offline, the one the account has first stays, and the other device's copy takes it at its next pull.
  - Every other save is an upsert by ID, and a delete of what is gone deletes nothing and succeeds.
- **Refused or tried again.** A change that fails is sorted by the account's answer:
  - Tried again later: no answer (status 0, which is also what a request given up after its 20 seconds returns), 408, 429 and 5xx, and anything that is not an answer from the account.
  - Session renewed, then sent again at once: 401. A renewal that fails leaves the change to be tried again later; one the service refuses signs the browser out (below).
  - Refused: any other 4xx, or a record turned down here before sending. The queue stops at it: the entry is marked with the answer and kept, nothing behind it is sent, and nothing is skipped or dropped. The app says how many records are not sent. The records stay on the device and are in a backup made of it. The refused change is tried again whenever the sender runs: after a write, when the network comes back, when the app comes back to the front, when the books open, on 重试, and after a wait once a later try has failed for want of a network. A try that fails for want of a network clears the mark, so the app says the records are waiting rather than refused; a refusal sets it again.
- **The pull** reads the whole space from the account, its summaries too though no backup holds them, and makes the copy match it in one local transaction: a record the account has is written unless a change to it is still to send, and a record the copy has that the account does not, with no change waiting, is deleted. It runs when the books open and when the app comes back to the front, after the outbox has been sent, and not while the browser says it has no network. Once it has changed anything, every query but the account's is invalidated, so the pages read again; nothing read is dropped.
- **The pull and the sender never meet.** The pull holds the same lock as the sender from before it reads the account until it has written the copy, so the sender cannot send a change and delete its entry between the read and its use, which would make a record the read did not have look deleted. Whether a record has a change waiting is read in the transaction that writes the copy, so a change a page makes meanwhile is either written before it, and kept as waiting, or after it, over what the pull wrote.
- **A pull is kept only for its own account.** Who the client is signed in as is read before the pull reads the account and again once it has: if it is not the account the books are for at either end, or the sender was stopped meanwhile (the books changed hands), what was read is let go, and nothing is written or marked as pulled. Under another account's session the space would read as empty, as row-level security hides its rows rather than refusing.
- **Opening offline.** The first opening of an account's books on a device needs a network: the account is read and its space pulled whole before any page shows. After that, what the app last read of the account (its space ID and name, whether it agreed, its name and code) is kept in this browser under `holdem-account.<user ID>`, and the books open from that and the copy: at once when the browser says it has no network, and otherwise when the account cannot be read for any reason but an answer that turns it down. Only an answer that the account is not there signs the browser out, as before. An account never opened on the device is still told its books cannot be reached.
- **The session offline.** The Supabase client keeps the session in storage. With no network and its access token run out, it cannot renew the token, keeps the session to renew later, and reports no session to `onAuthStateChange`. Before it reports anything it tries to renew the token for some 15 seconds. The app takes the session kept in storage (under the client's own key, now named in `data/supabase.ts`) as signed in: from the start when the browser has no network or the kept token has run out, and whenever the client reports no session while storage still holds one. The account's books then open at once; the client renews the token once it can. A renewal the service turns down removes the session, and the browser is signed out.
- **Signing out.** 退出登录, on 我的, on the page that says the books cannot be reached and on the first-entry step, first tries once more to send what is waiting. With nothing left, the browser signs out and the copy and what was kept of the account are deleted. With records left, it says how many, and on 保留并退出 signs out and keeps the copy, which is sent the next time the same account signs in here. Signing out offline is done: the client removes the session before it tries to tell the service, and the app no longer reports that as a failure. A sign-out the person did not ask for, as when the service refuses to renew the session, keeps the copy as it is, sent or not, until the same account signs in again.
- **Still online only**, each refused offline with nothing written: signing in, bringing guest records into the account ([ADR 0053](0053-guest-records-brought-into-an-account.md)) and restoring a backup. Each first sends the whole outbox under the lock; with no network, or with anything left unsent, it fails with `OnlineOnlyError`, which says which and how many, and nothing is written. It then reads the account into the copy, and if that read fails it fails the same way, with nothing written: what the step decides by, such as which games bringing guest records in counts as already in the account, is what the account holds. Only then does it go to the account itself (`restore_books`), and the copy is pulled to match again; a failure of that last pull is made good at the next one.
- **Several devices.** A record that can change (a game, a player, an insurance hand, a saved setting, a summary) is replaced by whichever device sends it last, as before. Another device sees it at its next opening or return to the front. Nothing is live, and nothing is merged by the time it changed: those are D.3 and D.1.
- **The app shows** how sending stands as the visual guide describes it ([section 5](../design/README.md#5-components)): a dot on 我的 while records wait, the 同步 row in 我的's settings, the alert at the top of every page once the account has turned one down, and the count in the sign-out step.

## Consequences

- A device that was offline for a long time sends its old copy of a game when it comes back, and that replaces a newer one another device sent meanwhile: a game settled on another device can go back to the state it was in here, while the summary of its settlement is still in the account. The reports then work the summary out again or drop it as the game stands. Until D.1, one device at a time should keep a given game.
- An account's records are now kept on every device that has opened its books, until the account signs out there with nothing left to send. Clearing the browser's storage with records unsent loses them, as a guest's books are lost.
- A refused change holds up everything after it, on purpose: sending later changes past it could send events for a game the account never received. A refusal that cannot be fixed by trying again needs a backup and a fix in the app.
- A page shows the copy, so what another device changed shows only after the next pull.
- Restoring a backup and bringing guest records in still need a network, and a device with records waiting has to send them first.
- The sign-out keeps the copy only with records left to send, so a device that is lent keeps no account's books once it is signed out with everything sent. A sign-out the person did not ask for keeps them.
- Three narrow windows are known and left as they are:
  - A record written in another tab of the same account at the moment this tab signs out, between the count of what is unsent and the deletion of the copy, is deleted with the copy and never sent.
  - The pull reads each list a page of 1000 at a time. A record deleted by another device while a longer list is read shifts the pages, and a record after it can be missed and deleted from the copy; the next pull brings it back. The account is not touched.
  - A delete of a record the copy does not have is not sent. A summary another device made of a game it settled, not yet pulled here, stays in the account when this device opens the game again and drops its summary; the reports work it out again from the game.
- This narrows ADR 0046: an account no longer reads and writes Supabase directly, a write is queued rather than failing with no network, and the books of an account opened on the device before are reachable offline.
